- **Full real OAuth2.1+PKCE flow via curl** (no browser tool): register client at `/oauth2/register` → GET `/oauth2/authorize?...&resource=...` with `Accept: text/html` (omitting this header causes the resource-server chain to intercept with a bare 401 `WWW-Authenticate: Bearer` instead of a login redirect) → extract `_csrf` from the login/consent HTML (`name="_csrf" value="..."` — note `type="hidden"` sits *between* those two attributes, so a naive regex expecting them adjacent will fail) → POST credentials to `/login` → re-GET the authorize URL (now redirects, not forwards, to the *custom* consent page with `client_id`/`scope`/`state` as query params — Spring's *default* built-in consent page renders in-place with a direct 200, but a *custom* `.consentPage(...)` is reached via a real 302 redirect instead) → POST consent (with CSRF) to `/oauth2/authorize` → follow redirect for the code → POST to `/oauth2/token` with `code_verifier` **and `resource` repeated at this step too** (the `resource` param must be sent at *both* the authorize and token steps — `ResourceIdentifierAudienceTokenCustomizer` reads it from the token-exchange request's own additional params, not from what was sent at authorize) → real Bearer token → call the actual endpoint.

5. **MCP connection visibility + per-client revocation** (`McpConnection`, `McpConnectionRepository`, `McpConnectionsController`, `AdminMcpPage.tsx` "Connected clients" section) — previously the *only* control was a blunt org-wide kill switch; this added a scalpel: list + individually revoke a specific client's authorization. Discovered along the way that `oauth2_authorization_consent` (the table in `V40__oauth2_authorization_server.sql`) is dead — `McpAuthorizationServerBeans` deliberately keeps consent in-memory only — so the new repository reads/deletes against the real, JDBC-backed `oauth2_authorization` table instead, joined to `users` for org-scoping. Also added `V49__index_oauth2_authorization_principal.sql` (no index existed on `(registered_client_id, principal_name)` in Spring's own default schema).

6. **Disabled-user MCP access fix** (`McpEnabledGuardFilter`) — a disabled/offboarded user's already-issued MCP *refresh* token kept minting new access tokens indefinitely, because Spring's refresh grant re-derives its principal from the stored `OAuth2Authorization` snapshot rather than re-checking live user status the way a fresh login does, and the separate per-user `mcpEnabled` flag isn't automatically flipped by disabling an account. Added a live `"ACTIVE".equals(user.status())` check to the same filter that already checked the org/user MCP toggles.

7. **Self-registered MCP clients could never actually get the `mcp.read` scope — the flagship "connect Claude Desktop" flow was completely non-functional** (`ConsentRequiringRegisteredClientRepository`). RFC 7591 requires a DCR request to omit `scope`; Spring's `DEFAULT_SCOPE_VALIDATOR` correctly rejects one that specifies it. Nothing in the app ever did the *other* half of that RFC contract (server decides what to grant) — a DCR client was left with a permanently empty scope set forever, and the resource server requires `SCOPE_mcp.read`. Fixed by granting `mcp.read` (the app's only issuable scope) to any client registering with an empty scope set. **Verified with a full real OAuth2.1+PKCE round trip** ending in a genuine `200` from a live `/mcp` `initialize` call — this is the strongest verification technique established this session and is documented in detail above.

8. **Branded MCP login/consent pages** (new `McpLoginConsentPageController`, wired via `McpSecurityConfig`'s `.loginPage("/login")` / `.authorizationServer(as -> as.authorizationEndpoint(e -> e.consentPage("/oauth2/consent")))`) — replaced Spring's plain unstyled defaults now that DCR clients can actually reach them (fix #7 made this reachable at all). Plain self-contained HTML (no templating engine in central-server), explicit CSP/Referrer-Policy/no-store headers. Shows the requesting client's human-readable name — which is attacker-controlled via DCR — properly `HtmlUtils.htmlEscape`'d (tested with a literal `<script>alert(1)</script>` client name). **Regression hit and fixed along the way**: setting a custom `.loginPage(...)` silently disables formLogin's automatic permit-all for the login page (confirmed live: unauthenticated GET `/login` started redirect-looping to itself) — fixed with an explicit `authorizeHttpRequests(auth -> auth.requestMatchers("/login","/login/**").permitAll().anyRequest().authenticated())`.

9. **Attack Surface Map cluster-overlap bug** (`webui/frontend/src/lib/attackSurfaceGraph.ts`) — user-reported: a WATCHLIST-type cluster visually sat on top of the platform/"own infra" cluster. Root cause: `layoutGraph`'s old per-cluster force-anchor points had WATCHLIST at `(0.5w, 0.85h)` and platform at `(0.14w, 0.78h)` — nearly the same horizontal band, separated only by an x-axis gap that a wide subdomain fan-out (via d3-force mutual repulsion) could bridge. Fixed by rearranging all four cluster anchors (OWN, COMPETITOR, WATCHLIST, platform) into a proper 2×2 grid so every pair differs on at least one axis by a real margin. **Notable methodology point**: the first regression-test attempt (centroid-to-centroid distance, OR-logic across axes) did *not* actually catch the bug — the old coordinates' large x-gap alone satisfied it despite the real y-axis collision. Replaced with a test that checks every node in each cluster (not just its centroid) against a minimum distance from the hub, and *empirically confirmed* (by temporarily reverting the coordinates and re-running) that this version does fail against the old buggy layout and pass against the fix.
